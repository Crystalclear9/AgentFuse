# Known Limitations

本文档明确说明 AgentFuse 首版**不做什么**以及**不保证什么**。
这些是设计边界，不是隐藏的缺陷。

---

## 0. 需求 §19 的 P2 条款完成情况

需求把能力分成 P0（必须）、P1（应当）、P2（可选）三级。下表逐条列出
**§19 中所有 P2 条款**的实现状态 —— 已实现的给出入口，**未实现的明确写出**，
不把没做的事说成做了。

| P2 条款 | 状态 | 入口 / 说明 |
|---|---|---|
| 可插拔调度策略 | ✅ 已实现 | `agentfuse/runtime/strategy.py`：`fifo`（默认）与 `sjf`（最短作业优先），由 `runtime.scheduling_strategy` 选择 |
| 会话内已完成结果复用 | ✅ 已实现 | `agentfuse/sharing/result_cache.py`：候选键 + 快照**内容** + 依赖复验三重校验；**默认关闭**（`result_cache_entries = 0`），因为开启会改变工作流的观测行为 |
| Worker 预热池 | ✅ 已实现 | `agentfuse/runtime/pool.py`：worker 是多任务进程，Runtime 空闲时预启动，`runtime.worker_pool_size`（默认 2） |
| 性能基线与回归守卫 | ✅ 已实现 | `benchmarks/baseline.json` + `scripts/check_regression.py`（容差同时考虑百分比、3 倍标准差与绝对噪声底线） |
| CI 工作流 | ✅ 已实现 | `.github/workflows/ci.yml`：Windows / Ubuntu / macOS × Python 3.11–3.13，跑 pytest + 验收自检 + 性能守卫 |
| 跨会话持久化结果缓存 | ❌ **未实现** | 只做了会话内缓存（§2.1）。跨会话复用需要一个跨进程的结果存储与失效策略，会引入"结果来自另一个会话"的可信度问题，因此首版**不做** |
| GPU 调度与 GPU KV Cache 管理 | ❌ **未实现** | Runtime 只调度本地 CPU 进程，不感知 GPU，也不管理显存 |
| 分布式执行 / 多节点调度 | ❌ **未实现** | 所有 worker 都在本机；快照与结果通过本地文件系统传递 |
| 多用户权限与认证 | ❌ **未实现** | Web 界面只监听 `127.0.0.1`，是本地单用户工具（§6） |
| 崩溃后的自动恢复执行 | ❌ **未实现** | 崩溃后只把未完成的运行标记为 `INTERRUPTED`（§6），不自动重放 |

> P2 条款**不影响** P0/P1 的验收：共享语义、依赖验证、资源控制、事件协议与
> 数据持久化全部按 P0/P1 实现，并各自有对应的自动化用例（见 `TEST_REPORT.md`）。

## 1. 工具与沙箱

### 1.1 首版仅支持受控工具

首版**仅支持受控工具**：共 **7 个内置工具**（6 个只读确定性工具 + 1 个故障注入测试夹具）。
其它工具必须先在 `ToolRegistry` 中注册，才能被调用。

### 1.2 不提供通用安全沙箱保证

`WorkspaceReader` 的路径边界检查、符号链接逃逸拒绝等机制，是**针对受控可信工具的
执行契约**，**不是**操作系统级的安全沙箱。

* 它不能阻止一个恶意工具直接调用 `open()` 绕过接口；
* 它不能限制进程的系统调用、注册表访问、网络访问；
* 它不提供容器 / microVM / seccomp 级别的隔离。

### 1.3 不支持任意程序的完整依赖追踪

如果一个工具绕过 `WorkspaceReader` 直接访问文件系统，AgentFuse **无法**确认它的
全部依赖。这类工具必须被标记为不可共享（`deterministic=False` 或 `read_only=False`），
否则其结果可能被错误复用。

因此：**"AgentFuse 追踪到了任意程序的所有文件操作"这句话是不成立的。**

### 1.4 首版不允许对任意 shell 命令自动开启共享

只有注册表中明确声明为 `deterministic=True` 且 `read_only=True` 的工具才会进入
共享协调器。

## 2. 共享语义

### 2.1 首版核心是"正在执行中的调用合并"（In-flight Sharing）

* 不提供跨进程重启、跨会话长期有效的通用结果缓存；
* 已完成的执行不会被后来的调用复用（后来的调用会自己执行一次）；
* 首版**没有**实现"有限的结果复用扩展"，因为它会影响在线共享的正确性验证路径。

### 2.2 候选键相同的调用也可能不共享

候选键只是**必要条件**。最终能否共享取决于依赖验证结果。
系统允许"该共享的没共享"（保守），不允许"不该共享的共享了"。

### 2.3 目录列表指纹只覆盖直接子项

`DIRECTORY_LIST` 指纹由直接子项的名称与类型构成，不递归。
子目录的内容变化需要通过该子目录自己的 `DIRECTORY_LIST` / `FILE_READ` 依赖体现。

### 2.4 共享成功率口径保守

只有真正收到他人执行结果的 Follower 才计入分子；Leader 不计入。
因此"2 个调用共享 1 次执行"的成功率显示为 50%。

## 3. 工作区快照

* **不实现**写时复制（Copy-on-Write）与块级去重；快照是普通文件复制。
* **不实现**进程级检查点 / 内存快照；快照只包含文件系统状态。
* **不实现**真正的文件系统层隔离。
* 快照是**逻辑不可变**的：AgentFuse 自己不写入快照目录，但**无法阻止**外部进程
  修改它。`SnapshotStore.verify_integrity()` / `check_integrity()` 可以检测这种修改，
  并且已经在**加入共享组之前**与**最终提交之前**接入验证路径（被篡改的快照会被
  拒绝共享）。校验需要重新扫描文件树，因此结果按快照缓存。
* 单个快照上限：5000 个文件 / 64 MiB（`config/default.toml` 可调）。
* 默认排除 `.git`、虚拟环境、缓存目录、`*.pyc` 等。

## 4. 资源管理

### 4.1 内存预算不等于操作系统硬限制

必须严格区分三件事：

| 名称 | 含义 | 是否强制 |
|---|---|---|
| `reserved_estimate_mb` | 工具注册时声明的**预估**内存，用于**准入控制** | 否（只是估算） |
| `observed_rss_mb` | psutil 采样到的**实测** RSS，用于**报告与告警** | 否 |
| OS 硬限制 | 操作系统层面的内存/进程限制 | **首版未实现** |

当实测 RSS 超出预算时，资源控制器会**阻止新的任务进入执行**并发出告警，
但**不会**杀掉正在运行的超额进程。

### 4.2 CPU 时间精度受操作系统限制

worker 自测的 `time.process_time()` 在 Windows 上以约 15.6 ms 的量子计费，
因此小于该量级的工具会显示 `cpu_time = 0`。这是操作系统的计量粒度，不是测量错误。

### 4.3 调度策略是简单 FIFO

首版不实现 SLO-Aware / Goodput-Aware / 可抢占调度。
后续可以在同一套 ResourceScheduler 接口上扩展。

### 4.4 Worker 启动开销显著

工具在独立进程中执行，进程启动本身需要约 120–200 ms（解释器启动 + 导入）。
对于计算量很小的工具，这个开销会主导 makespan —— 这也是 `shared` 场景在
**worker=2** 时加速比只有 1.00x 的主要原因。

### 4.4a Worker 预热池的内存代价

`runtime.worker_pool_size`（默认 2）个 worker 进程会在 Runtime 启动时预热，
每个大约占用 20–30 MiB 常驻内存。空闲的 worker 不占用执行槽位，但会占用内存。
对内存极度受限的环境可以把该值设为 0（每次执行新建进程，代价是 ~99 ms 冷启动）。

### 4.5 共享执行不会缩短"资源充裕"时的墙钟时间

当 worker 数足够、两次计算本来就能**并行**执行时，共享执行节省的是
**计算量**（CPU 时间减半），而不是墙钟时间。真正的延迟收益出现在
**资源受限**（worker=1）时：baseline 必须把两次计算排队串行执行。
实测数据见 `BENCHMARK.md` §6。

---

### 4.6 Windows venv 使用 launcher 打手

在 Windows 上，虚拟环境的 `python.exe` 是一个 **launcher**：它会再启动真正的解释器
（子进程）。因此 `Popen.pid` 与真正执行工具的 pid 不同：

* `physical_executions.worker_pid` 保存的是 launcher pid（启动器）；
* `physical_executions.worker_root_pid` 保存的是**真实** worker pid（worker 通过 `hello` 消息上报）。

两者都会被终止，但只看 `worker_pid` 很容易误判（launcher 可能已经退出）。

### 4.7 进程终止的平台差异

* **Windows**：虚拟环境使用 **launcher 打手**，`Popen.pid` 是 launcher，
  真正执行工具的是它的子进程。杀掉 launcher 只会关闭管道，
  正在计算的 worker 不会再读 stdin → 它会成为孤儿。
  因此 worker 启动后的第一句话是 `hello`，它报告自己的**真实 pid**；
  Runtime 同时用 `psutil` 发现 launcher 的子进程作为兜底。
* **Linux / macOS**：虚拟环境的 `python` 就是真实解释器，**没有 launcher 打手**。
  Runtime 会通过 `sys.base_prefix` 判定是否可能存在存根，在没有存根的平台上**不做等待**（启动开销从 1010 ms 降到 5 ms）。
* 两种平台上的实际 worker pid 都会写入 `physical_executions.worker_root_pid`，
  而 `worker_pid` 保留 launcher pid。

## 5. Agent 与模型

* **Scripted Agent 不是 LLM Agent。** 它是按照真实结果动态选择下一步的本地程序，
  不具备语言模型的推理能力，也不宣称具备。
* AgentFuse **不实现** Agent Framework、**不训练**模型、**不实现**推理引擎。
* AgentFuse **不依赖**任何特定框架的内部 Scheduler 或状态对象。
* Agent 实体运行在宿主进程的 asyncio 事件循环中；**只有工具计算**运行在独立进程中。
  Agent 本身不做重 CPU 计算。

## 6. 其它

* **快照不包含进程内存**（不保存进程内存、寄存器或正在运行的线程状态）。
* **不实现** GPU KV Cache 管理、**不实现** GPU 调度、**不实现**分布式执行、
  **不实现**多节点调度。
* 只在 **Windows 11** 与 **WSL2 / Ubuntu-22.04** 上实测通过；**macOS 未验证**。
* **同一个 home 目录不能同时被两个 AgentFuse 实例使用**（例如一边跑 Web 服务、
  一边在 WSL2 里跑 CLI）：SQLite 的 WAL 锁在跨操作系统的挂载盘上无法共享，
  第二个实例会收到 `disk I/O error`。此时 Runtime 会给出明确提示，请停止另一个
  实例或用 `AGENTFUSE_HOME` / `--home` 指向不同目录。
* WSL2 需要 Python 3.11+（Ubuntu-22.04 自带的是 3.10），推荐用 `uv` 在项目目录内
  创建虚拟环境（见 README §4）。
* **不实现**跨会话持久化结果缓存（P2，详见 §0）。
* **不实现**复杂的多用户权限系统。
* Web 界面默认只监听 `127.0.0.1`，**没有**内置认证 —— 它是本地单用户工具。
* Web 界面**不加载任何 CDN 资源**，前端是纯原生 HTML/CSS/JS，无构建链。
* 前端脚本**没有被端到端执行**：CI 校验它的语法（`node --check`）与它依赖的
  后端字段，但没有无头浏览器去点击页签。前端逻辑的错误因此只能靠人工验证 ——
  后端返回的真实数据是逐字段断言的（验收自检），界面本身的渲染不是。
* Runtime 进程被强杀时，已经死亡的运行记录会被标记为 `INTERRUPTED`
  （通过缺失的 `end_time` 与 `status` 体现），不会误判为完成；
  首版**不提供**崩溃后的自动恢复执行。
* Windows 上 CPU 时间的计量粒度、空闲时 RSS 读数偏低等平台差异，
  会让不同机器之间的绝对数值不可直接比较。
